## О проекте

«Запись на звонок» — упрощённый сервис бронирования времени по мотивам [Cal.com](https://cal.com). Владелец календаря публикует типы встреч, гость выбирает свободный слот и записывается на звонок. Авторизации, личных кабинетов, внешних календарей и уведомлений нет.

## Сценарий: от типа встречи до записи у владельца

1. **Владелец** открывает раздел владельца (без входа — владелец один и задан заранее).
2. Создаёт тип встречи: название «Знакомство», описание «Короткий созвон», длительность 30 минут.
3. Тип встречи появляется в каталоге типов встреч.
4. **Гость** без регистрации открывает каталог и выбирает тип «Знакомство».
5. Видит календарь на ближайшие 14 дней и выбирает день.
6. Видит свободные слоты дня длительностью 30 минут и выбирает время.
7. Вводит имя и email и подтверждает запись.
8. Получает подтверждение и секретную ссылку для отмены. Пока запись действует, пересекающиеся слоты недоступны для всех типов встреч.
9. **Владелец** открывает список предстоящих записей и видит новую: тип, время, имя и email гостя, статус «Действующая».

Если два гостя одновременно записываются на пересекающееся время, успешна только одна запись, второй гость получает ошибку конфликта и выбирает другой слот.

Если планы меняются, **гость** открывает секретную ссылку, проверяет детали и нажимает «Отменить запись». Гость видит «Запись отменена», а владелец видит ту же запись со статусом «Отменена». Другой гость может занять освободившееся время, в том числе выбрать слот другой длительности, частично пересекающий отменённый интервал.

## Обязательные функции

Владелец:

- создаёт типы встреч (название, описание, длительность в минутах);
- смотрит список предстоящих записей всех типов встреч одним списком.

Гость:

- смотрит каталог типов встреч;
- смотрит свободные слоты выбранного типа на 14 дней вперёд;
- записывается на свободный слот (имя, email);
- отменяет запись по секретной ссылке до её начала.

## Правила записи

- Окно записи: 14 календарных дней, начиная с сегодняшнего; окно сдвигается каждый день. Прошедшие слоты не предлагаются.
- Часовой пояс сервиса: UTC. Время в API передаётся в ISO 8601 (UTC), интерфейс показывает локальное время гостя.
- Рабочие часы владельца: ежедневно 09:00–18:00 UTC. Встреча должна закончиться не позже 18:00.
- Длительность слота равна длительности типа встречи. Шаг доступных стартов — 30 минут.
- Пересечение интервалов действующих записей запрещено, включая частичное наложение разных типов встреч. Интервалы полуоткрытые `[start, end)`: следующая встреча может начинаться в момент окончания предыдущей.
- Правило действует для одновременных запросов: проверка и сохранение записи выполняются атомарно, сервер отвечает HTTP 409 на конфликт.

## Правила отмены

- Открытие и перезагрузка секретной ссылки показывают детали без изменения записи. Отмена требует нажатия «Отменить запись» и действительного кода из ссылки.
- Отменить можно только действующую запись строго до её начала. Отмена необратима и освобождает интервал для всех типов встреч с учётом остальных правил записи.
- Владелец видит действующие и отменённые записи до их запланированного окончания, в порядке времени начала и без секретных ссылок и кодов.

## Ограничения

- Один владелец календаря, без авторизации и личных кабинетов.
- Нет интеграций с внешними календарями и уведомлений.
- Нет переноса записей.
- Данные хранятся в памяти процесса: перезапуск сервера сбрасывает типы встреч и записи.

### Агент OpenCode (`opencode.yml`)

Агент отвечает на команды в обсуждении issue или PR и в комментарии к строке diff. Например: `/oc explain this issue`, `/oc запусти скилл to-spec по обсуждению этого issue`.

- **Команды (`mentions`):** `/opencode`, `/oc` — набор OpenCode по умолчанию, записан явно. В PR команда пишется в начале комментария: `/oc <задача>` или `/opencode <задача>`, задача может идти и со следующей строки. Так упоминание `/oc` или пути `.github/workflows/opencode.yml` в тексте не тратит попытку бюджета. Выражения GitHub не умеют регулярные выражения, поэтому слово вроде `/october` в начале комментария в PR тоже запустит агента. В обычных issue правило прежнее: команда срабатывает в любом месте текста.
- **Кто может вызвать:** автор комментария с `author_association` `OWNER`, `MEMBER` или `COLLABORATOR`. Комментарии ботов игнорируются, поэтому агент не отвечает сам себе. `opencode github run` дополнительно проверяет у автора права `write` или `admin`. `pull_request_target` не используется, чужие fork ключ модели не получают.
- **Модель:** `opencode/gpt-6.2-sol` через OpenCode Zen, оплата с баланса Zen ($2 / $10 за 1M токенов входа / выхода). Ключ — секрет `OPENCODE_API_KEY`. Первый triage шёл на бесплатной `opencode/big-pickle`; спецификацию, тикеты и реализацию ведёт модель сильнее. Модель меняется одной строкой `OPENCODE_MODEL` в `env` воркфлоу: её берут и action для issue, и прямой запуск `opencode github run` в PR. Служебная модель для заголовков сессий задана в `opencode.json` (`small_model`) и остаётся бесплатной `big-pickle`.
- **`share: false`:** сессии агента не публикуются. Репозиторий открытый, а сессия содержит контекст задачи. Результат виден в комментарии и в логе прогона.
- **Права:** стандартная авторизация OpenCode. `contents: read` и `id-token: write`: Actions обменивает OIDC-токен на токен GitHub App `opencode-agent`, и агент комментирует и пушит правами приложения. У checkout `persist-credentials: false`.
- **Трекер:** задачи репозитория — GitHub Issues `alex1alrus/ai-for-developers-project-387`. Агент читает issue через `gh issue view <номер>`; правила работы с трекером — `docs/agents/issue-tracker.md`, общие правила — `AGENTS.md`. Спецификация и решения первого проекта читаются через `gh issue view <номер> -R alex1alrus/ai-for-developers-project-386`, новые задачи туда не пишутся.
- **Отличие от стандартной настройки:** добавлены `issues: write`, `pull-requests: read`, `actions: read` (история прогонов для предела запусков в PR) и `GH_TOKEN: ${{ github.token }}`. `opencode github run` не передаёт токен приложения в shell агента, поэтому скиллы работают с трекером через `gh`: triage ставит метки и комментирует, to-spec и to-tickets создают issue. Эти действия видны от `github-actions[bot]`. Код и PR этот токен только читает; коммиты, PR и итоговый ответ агента идут через приложение `opencode-agent`.
- **Ограничения:** `concurrency` по номеру issue или PR: в одном обсуждении работает один агент. Для issue действует тайм-аут задания 30 минут.
- **Скиллы на раннере:** проектные скиллы лежат в `.claude/skills/`, OpenCode читает этот путь сам: `ask-matt`, `code-review`, `codebase-design`, `diagnosing-bugs`, `domain-modeling`, `grill-me`, `grill-with-docs`, `grilling`, `handoff`, `implement`, `implement-spec`, `improve-codebase-architecture`, `pr`, `prototype`, `research`, `retro`, `setup-matt-pocock-skills`, `tdd`, `to-spec`, `to-tickets`, `triage`, `wayfinder`, `wizard`. Ещё доступен встроенный `customize-opencode`. Настройки трекера (`docs/agents/`) и правила (`AGENTS.md`) приходят с checkout.
- **Проверки:** команда `mise run check` — проверка генерации (`gen:check`), линтер, типы, тесты, сборка и браузерный сценарий; тот же прогон в pre-commit хуке и в CI.
- **Остановка:** Actions → прогон → Cancel workflow останавливает текущий запуск. Actions → opencode → Disable workflow отключает будущие. Ключ можно отозвать в консоли opencode.ai.
- **Ветку создаёт раннер:** перед сессией `opencode github run` переключается на свою ветку (`opencode/issueN-…` для issue, ветка PR для PR) и после сессии пушит только её. Проверяется только имя ветки в конце сессии: если `HEAD` основного checkout стоит на другой ветке или отсоединён, раннер пишет в лог `Branch changed during chat`, ничего не пушит и PR не открывает, а коммиты пропадают вместе с раннером. Ответ агента при этом всё равно публикуется комментарием, поэтому потерю легко не заметить: так в #6 потерялась первая реализация (прогон [44709761835](https://github.com/alex1alrus/ai-for-developers-project-387/actions/runs/44709761835), скилл `implement-spec` создал свою integration branch). Поэтому `AGENTS.md` запрещает агенту в Actions переключать ветку checkout: integration branch скилла — ветка раннера, дополнительные ветки и worktree агент сливает в неё до конца сессии.
- **Файлы воркфлоу агент не пушит:** у приложения `opencode-agent` нет права `workflows`, GitHub отклоняет push с изменениями в `.github/workflows/`. Такие правки агент готовит, а коммитит человек.

#### Предел запусков на один PR

В [`opencode.yml`](.github/workflows/opencode.yml) у каждого PR есть бюджет из трёх попыток. Команды в обсуждении PR и на строках diff расходуют общий бюджет; отмена, тайм-аут и Re-run тоже считаются. Команды в обычных issue работают без этого ограничения.

Перед запуском агента воркфлоу читает историю своих прогонов в GitHub Actions (`actions: read`). Он учитывает допущенные запросы по номеру PR в имени прогона и число попыток `run_attempt`. Комментарии, пропущенные фильтром, в счётчик не попадают. Учитываются прогоны с момента активации правила, пока они доступны в истории Actions.

Когда бюджет исчерпан, модель не вызывается. Если запуск заблокирован или остановлен из-за ошибки либо тайм-аута (25 минут на вызов OpenCode), отдельное задание публикует причину, последний head SHA PR, ссылку на логи, число использованных попыток и статус «нужен человек». При отмене комментарий появится, если GitHub запустит задание отчёта.

Администратор может изменить `PR_ATTEMPT_LIMIT` или условия допуска в `.github/workflows/opencode.yml`. У нового PR свой бюджет; новый коммит в том же PR его не сбрасывает.

Условие допуска в PR записано дважды: в `run-name` (по нему проверка находит текущий прогон в истории) и в `if` задания. Выражения GitHub нельзя переиспользовать, поэтому тест `scripts/opencode-workflow.test.ts` в `mise run check` разбирает оба условия и требует одинаковый набор проверок для PR, а для обычных issue — прежнее правило `contains`. Тот же тест запускает шаг проверки бюджета с подменённым `gh` на записанной истории прогонов: третий запрос проходит, четвёртый получает `limit_exhausted`, Re-run тратит попытку, прогоны других PR не считаются, без текущего прогона в истории проверка падает.

Известные ограничения:

- **Re-run прогона, созданного до активации лимита,** идёт по той версии воркфлоу, где проверки ещё нет. Так GitHub выполняет любой Re-run; новые PR это не затрагивает.
- **Комментарий к строке diff в PR из fork** пропускается: GitHub даёт такому событию токен только на чтение и не передаёт секреты, поэтому ни агент, ни отчёт там работать не могут. Общий комментарий в fork-PR проходит обычный путь.
- **`actions: read`** выдано всему заданию агента, потому что проверка стоит в нём же: иначе «Re-run failed jobs» перезапустил бы агента без проверки. Репозиторий публичный, история и логи Actions и так открыты.
- **Слово вроде `/october` в начале комментария в PR** тратит попытку: выражения GitHub без регулярных выражений.
- **Re-run старого прогона в момент, когда новый запрос ещё ждёт раннер,** может заставить оба прогона посчитать друг друга целиком и остановиться с `limit_exhausted`: PR получит меньше трёх вызовов модели, но не больше.
- **Ожидающий запрос может быть вытеснен.** В группе `concurrency` GitHub держит один выполняющийся и один ожидающий прогон; третья команда подряд отменяет ожидающую. Отменённый прогон тратит попытку; отчёт покажет `cancelled`, а если бюджет к этому моменту исчерпан — `limit_exhausted`.
- **Комментарий к строке diff запускает воркфлоу из ветки PR**, а общий комментарий — из `main`. PR, который меняет `opencode.yml`, для комментариев к строкам работает по своей версии лимита. Менять воркфлоу может только человек с правом `workflows`, агент такие файлы не пушит.
- **Проверка листает всю историю прогонов `opencode.yml`** (каждый комментарий создаёт прогон) за 2 минуты; на очень длинной истории она начнёт падать с `infra`. Тогда сузить запрос по дате создания PR.

### Автотриаж новых обращений (`triage.yml`)

OpenCode запускается при открытии issue пользователем с ролью `OWNER`, `MEMBER` или `COLLABORATOR`. Issue от ботов и issue, уже открытые с меткой [`ready-for-agent`](docs/agents/triage-labels.md), пропускаются. Эту метку ставят `to-spec` и `to-tickets` при создании готовых задач.

Агент разбирает обращение по скиллу `triage`, сверяется с текущим поведением приложения и ставит метки категории и состояния. Если данных не хватает, он ставит `needs-info` и задаёт автору конкретные вопросы в issue. Код приложения не меняется. Для повторного разбора после ответов можно вызвать `/oc` в обсуждении.

Воркфлоу использует те же модель, права и `GH_TOKEN`, что и `opencode.yml`. Лимит — 30 минут; общая группа `concurrency` по номеру issue не даёт автоматическому и ручному запускам работать над одним обращением одновременно.

Номер issue передаётся в `prompt` через `github.event.issue.number`: в отличие от команды `/oc`, у события `issues` нет комментария, из которого агент берёт контекст. Заголовок и текст в `prompt` не подставляются, агент читает их через `gh`, чтобы текст обращения не становился инструкцией воркфлоу. В `opencode.json` стоит `permission.external_directory: deny`: без этого агент запрашивает доступ к файлам вне репозитория (например, к файлу события), в Actions ответить некому, и прогон висит до тайм-аута.

### Авторевью PR и браузерная проверка head SHA

Воркфлоу [`review.yml`](.github/workflows/review.yml) и [`browser.yml`](.github/workflows/browser.yml) агент подготовил в `.github/workflows-draft/`, человек перенёс их в `.github/workflows/` (у `opencode-agent` нет права `workflows`). Для обоих воркфлоу действует `pull_request` с событиями `opened`, `synchronize`, `reopened`, `ready_for_review`: новый прогон отменяет устаревший в своей группе по номеру PR.

- **Авторевью** идёт только для PR из ветки этого репозитория, если автор — `OWNER`, `MEMBER`, `COLLABORATOR` или `opencode-agent[bot]`. Черновики (draft) пропускаются, чтобы не тратить кредит модели: первое ревью запускается при переводе PR в ready. Задание за 15 минут собирает через `gh` diff, описание PR, связанные GitHub-тикеты и комментарии, обсуждение PR с прошлыми авторевью и разбором замечаний (повторное ревью не повторяет отклонённые человеком замечания без нового довода), коммиты PR с авторами и `Co-authored-by`, правила репозитория (`AGENTS.md`, а если PR меняет `.github/` — раздел README о воркфлоу), diff с SHA прошлого авторевью (повторное ревью проверяет в первую очередь правки после него; diff строится, только если прошлый SHA — предок head, после force-push или rebase ревьюер проверяет весь PR, а коммиты слияния помечены: изменения из `main` ревьюер проверяет только на конфликты с правками PR, изменения другой рабочей ветки и разрешение конфликтов — как правки PR), статусы проверяемого SHA и запускает новую сессию `opencode run` (`opencode/gpt-6.2-sol`, секрет `OPENCODE_API_KEY` только на этом шаге). Токен для чтения контекста имеет права `contents`, `issues`, `pull-requests`, `actions`, `checks` и `statuses` только на чтение. Агенту запрещены правка файлов и shell-команды. `REVIEW.md` и `opencode.json` берутся из базовой ветки; пока в ней нет `REVIEW.md` (PR, который его добавляет), используются краткие критерии из самого `review.yml`.
- **Формат.** Модель возвращает JSON: итог, замечания с уровнем (`blocker`, `major`, `minor`, определения в `REVIEW.md`), файлом, строкой, описанием и тем, как исправить словами, и список пробелов в согласовании и проверках. Шаг без модели собирает из него GitHub Review: сверху `### Авторевью <sha>` и счётчик 🔴 blocker · 🟠 major · 🟡 minor · ⚪ пробелы, итог, замечания вне строк diff и пробелы; замечания к строкам, которые есть в diff новой версии файла, становятся комментариями к этим строкам. Кружок ставит шаг сборки ревью без модели, а не сама модель. Готового кода (`suggestion`) нет: правку делает агент по команде человека, например ответом `/oc исправь как предложено` в ветке комментария. Сборка проверена тестом `scripts/review-payload.test.ts`.
- **Публикация** за 5 минут скачивает подготовленный запрос из артефакта `review-<sha>` и отправляет его в `POST /pulls/<n>/reviews` (`event: COMMENT`), если head и base всё ещё совпадают с проверенными. Если GitHub отклоняет комментарий к строке (HTTP 422), тот же текст публикуется одной сводкой; при другой ошибке задание падает, чтобы ревью не вышло дважды. Тело ревью обрезается до лимита GitHub, полный ответ модели лежит в артефакте. Если ответ модели не разобран как JSON нужной формы (объект со списком `findings`), ревью показывает его как есть с пометкой, без счётчика и без «дефектов нет»; если часть замечаний отброшена как неполная, ревью пишет, сколько. У задания только `pull-requests: write`, без ключа модели. Авторевью не продолжает сессию реализации и не меняет код; правки по замечаниям запускает человек командой `/oc`.
- **Принятый риск:** на `pull_request` GitHub выполняет YAML из ветки PR, а не из `main`. Ключ модели получают только ветки этого репозитория; изменить в них воркфлоу может только участник с правами записи и `workflows`, у которого и так есть доступ к секретам. `pull_request_target` не используется, PR из fork ключ не получают. Этот пункт записан в `REVIEW.md`, чтобы авторевью не повторяло его как дефект.
- **Браузерная проверка** идёт и для PR из fork, с `contents: read`, без ключа модели. Задание за 20 минут делает checkout `pull_request.head.sha`, сверяет его с `git rev-parse HEAD` и запускает Chromium с `--trace on` и скриншотами. На странице прогона Actions в Artifacts ищите `browser-<sha>`: `head-sha.txt` содержит проверенный SHA, `result.txt` — итог Playwright, `playwright/` — доступные трассы и скриншоты. Сверяйте SHA с последним коммитом PR.

### Проверка заголовка и описания PR (`pr-check.yml`)

В настройках репозитория (Settings → General → Pull Requests) разрешён только squash merge: заголовок коммита — заголовок PR, тело коммита пустое. Так в `main` попадает ровно одно сообщение на PR, а сообщения отдельных коммитов ветки и текст описания не становятся записями changelog. По этим сообщениям release-please собирает changelog и версию. Поэтому формат проверяется кодом, а не только правилом в `AGENTS.md`: `pr-check` падает, если заголовок не по Conventional Commits, хотя бы один раздел [шаблона](.github/pull_request_template.md) отсутствует или пуст или в разделе «Тикеты» нет строки, которая начинается с `Closes #N` (или `Fixes`, `Resolves`; можно со списочным `-` или `*` и пояснением после номера). Заголовки внутри блоков кода ``` и ~~~ не считаются разделами: блок закрывается только строкой из той же ограды не короче открывающей, поэтому внутренний ``` в блоке ```` остаётся кодом. Сам блок заполняет свой раздел, например вывод команды в «Проверках». HTML-комментарии `<!-- -->` GitHub скрывает, проверка тоже. Незакрытый `<!--` в начале строки скрывает весь остаток описания, а внутри строки это обычный текст. У PR от release-please (ветка `release-please--*` и автор `github-actions[bot]`) проверяется только заголовок. Поведение проверки закреплено тестом `scripts/pr-check.test.ts`. Задание без секретов и checkout, заголовок и описание берутся из события; правка описания (`edited`) запускает проверку заново. Статус `pr-check` обязателен в ruleset для `main` вместе с `check`.

Сообщения отдельных коммитов в ветке PR этим не проверяются: в `main` они не попадают. `opencode github run` коммитит незакоммиченные агентом изменения с резюме сессии, поэтому такие коммиты в ветке возможны.

Ограничения:

- **Сообщение squash-коммита можно изменить в окне мержа.** GitHub подставляет заголовок PR, но человек может его отредактировать, и `pr-check` этого не увидит. Перед мержем сверяй сообщение с заголовком.
- **PR, созданный кнопкой Revert,** получает заголовок `Revert "…"` без раздела шаблона: перед мержем переименуй его в `revert: …` и заполни описание.
- **Незакрытый блок кода или блок с отступом** проверка не распознаёт, заголовки в нём считаются разделами.
- **Re-run старого прогона `pr-check`** проверяет заголовок и описание на момент того события, а не текущие. После правки описания проверка запускается сама (`edited`).
- **PR release-please не получает проверок автоматически.** Он создаётся через `GITHUB_TOKEN`, а такие события воркфлоу не запускают, поэтому обязательных `check` и `pr-check` на нём нет. Release-PR мержит администратор в обход ruleset после ручной сверки changelog и версии.
