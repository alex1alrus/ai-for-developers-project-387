# Выводы о работе GitHub-агента

Личные выводы мейнтейнера по шагам курса, где OpenCode работал в GitHub Actions: команды `/oc`, автотриаж, авторевью и аудит по расписанию. Почти каждый вывод опирается на прогон, issue или PR.

## Что потребовало уточнений в постановке

- **Ветка раннера.** Скилл `implement-spec` велит создать integration branch. Агент сделал `git switch -c`, а раннер сверяет только имя ветки, поэтому ничего не запушил. Работа прогона [44709761835](https://github.com/alex1alrus/ai-for-developers-project-387/actions/runs/44709761835) пропала. После этого в `AGENTS.md` появилось правило оставаться на ветке раннера (#26, PR #27), и повторный прогон открыл PR #28. Инструкции скиллов агент выполняет буквально, даже если они противоречат тому, как устроен раннер. Ограничения раннера нужно записывать в `AGENTS.md` явно.
- **Право `workflows`.** У App `opencode-agent` нет права `workflows`, поэтому push в `.github/workflows/` отклоняется. Прогон [44733824695](https://github.com/alex1alrus/ai-for-developers-project-387/actions/runs/44733824695) написал `audit.yml`, а коммит пропал вместе с раннером. Код удалось восстановить из вызовов `apply_patch` в логе (PR #37). Обходной путь через `.github/workflows-draft/` был описан только в `REVIEW.md`, который читает ревьюер, а не исполнитель. Теперь он есть и в `AGENTS.md`. Правило, которое нужно исполнителю, должно лежать в его инструкциях.
- **Заголовок и описание PR.** Заголовок генерирует раннер отдельной моделью, которая не видит `AGENTS.md`. Описанием PR становится ответ агента, а не шаблон. Правило `AGENTS.md` «заполни каждый раздел шаблона» поэтому не работает: PR открывает раннер, а не агент. В #28 и #50 `pr-check` упал по обеим причинам, заголовок и описание поправил человек. Соблюдение требований к PR обеспечивает только `pr-check`, агент на него не влияет.
- **События `schedule` и `workflow_dispatch`.** Ответ агента здесь уходит только в лог: issue, куда его прокомментировать, нет. Журнал и issue по находкам пришлось явно поручить агенту в prompt.

## Что изменилось в настройках

- **Автотриаж.** Переведён на `GITHUB_TOKEN` с `contents: read` и без OIDC (#22, PR #34). Агент физически не может запушить код или открыть PR. Граница проходит по правам токена, а не по prompt.
- **`edit: deny`.** Этот запрет не распространяется на shell: файл можно создать через bash. Если рабочее дерево станет грязным, раннер на `schedule` попытается его закоммитить. Поэтому prompt аудита требует писать временные файлы только в `$RUNNER_TEMP`, а отчёты лежат вне checkout.
- **CI на `pull_request`.** `ci.yml` теперь запускается на `pull_request` (#30, PR #31). Release-PR, созданный через `GITHUB_TOKEN`, иначе оставался без проверки `check`.
- **Аудит.** Минимальные права заданий. Ветка проверяется в shell с учётом регистра, потому что выражение `if:` регистр не различает. У каждой попытки свой артефакт, и issue продолжают ссылаться на отчёт, по которому созданы.

## Ревью: где агент помог и где нет

- **Авторевью на PR #37** прошло семь раундов и не сошлось: каждый раунд давал 1–2 major. Почти все замечания касались Re-run и порядка измерений в prompt. Каждая правка закрывала один сценарий, а ревьюер находил следующий. Логику с состояниями (ключ находки, порядок прогонов, повторы, закрытые дубли, лимит) нельзя проверить тестами, пока она записана на естественном языке. Её место в детерминированном шаге с тестами, а агенту остаётся писать текст. Это вынесено в #38. Раунды остановлены по моему решению, оставшиеся замечания записаны как принятые ограничения.
- **Второй ревьюер (отдельная модель перед каждым push)** находил реальные ошибки до того, как их видел CI: апостроф, ломавший `jq` внутри строки bash; выбор категории через `max_by`; сценарий, при котором Re-run создавал «вернувшуюся» находку. Мои схемы он при этом подтверждал, а авторевью потом их пробивало. Два ревьюера с разным контекстом дополняют друг друга, но ни один не заменяет тест.
- **Бюджет попыток** на PR (`PR_ATTEMPT_LIMIT`) сработал: четвёртый `/oc` в #28 получил `limit_exhausted` (прогон [44721852455](https://github.com/alex1alrus/ai-for-developers-project-387/actions/runs/44721852455)). Без него каждая команда `/oc` в PR тратила бы кредит модели.

## Что показали прогоны аудита

- **Дубли не создаются.** Повторный прогон отметил четыре находки как «уже есть в #41–#44» и ничего не продублировал. Отложенные из-за лимита находки стали #46 и #47 (журнал #39).
- **Одиночный замер performance шумит.** Оценка упала с 0.98 до 0.91 между двумя запусками подряд. FCP (#40) прошёл порог, а Total Blocking Time (#45) и Max Potential FID (#48) появились как новые находки. Для числовых метрик нужна медиана нескольких замеров или отдельный порог. Без этого аудит заводит лишние задачи.
- **Лимит в пять issue за прогон** оказался полезен: первый же живой запуск дал семь находок.

## Итог

Агент хорошо справляется с ограниченной задачей: есть понятный prompt, узкие права и проверка, которая не зависит от модели (`check`, `pr-check`, права токена). Слабые места — правила, которых нет в его инструкциях, и логика состояний в prompt. Человек нужен в трёх местах: решить, какие находки брать в работу, остановить ревью, которое не сходится, и перенести то, что агенту запрещено правами.

Для команд, которые работают в GitHub, готовая интеграция OpenCode подходит как старт: `/oc`, триаж и запуски по расписанию заработали без своей инфраструктуры. Но многие шаги выше обходят поведение готового раннера: он сам выбирает ветку, генерирует заголовок PR, берёт описание из ответа агента, коммитит грязное дерево и упирается в права App. Авторевью, браузерную проверку head SHA, бюджет попыток и `pr-check` пришлось писать самим: отдельными воркфлоу и шагом бюджета в `opencode.yml`. Решения, заточенные под конкретный процесс в компании (свои шаблоны задач и PR, правила веток, согласования, трекер), работают лучше универсального раннера. В них поведение задаёт процесс, а не приходится подстраиваться под допущения инструмента.

Для меня предпочтительнее другой подход: движок процессов, где агент — один из типизированных шагов графа. У каждого шага есть вход и выход по схеме. Исход шага пересчитывает код, а не слова агента, и переход по графу идёт только по этому исходу. Граф с лимитами петель и возможности шагов проверяются до запуска. Состояние и журнал хранятся на диске, поэтому run продолжается после сбоя, и оплаченная попытка не теряется. Решение человека — явный шаг графа с записью, кто и как ответил. Ограничения агента (права, песочница, цена) собраны в одном adapter. В такой схеме логика дублей аудита была бы шагом-кодом с тестами (как предлагает #38), а не prompt. Работа агента не терялась бы из-за отказа push в конце одноразового раннера.
